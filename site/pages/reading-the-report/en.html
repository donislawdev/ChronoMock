Reading the report

At the end of a session, chrono run prints a report: whether the date reached the application, which clocks it read and how often, how it ended and what to keep in mind. This page goes through it line by line.

An example

A session on a small test application that shows the date it reads, closed from its own window after a few seconds: 

chrono run C:\apps\test.exe --at 2038-01-19T03:14:07 --zone +00:00
Chrono Mock - session report
  target:   C:\apps\test.exe
  verdict:  WORKS - time substitution took effect  (processes: 1)
            every process that read time saw the session clock
  session:  fake clock reached 2038-01-19T03:14:11
            real elapsed 4.5s, fake elapsed 4.5s
  exited:   the target closed itself with code 0
  covered channels (substituted, with call counts, 30 calls in all):
            - pid 101552: GetSystemTimeAsFileTime (1 call)
            - pid 101552: GetSystemTimePreciseAsFileTime (0 calls)
            - pid 101552: GetSystemTime (0 calls)
            - pid 101552: GetLocalTime (19 calls)
            - pid 101552: NtQuerySystemTime (10 calls)
            - pid 101552: GetTimeZoneInformation (0 calls)
            - pid 101552: GetDynamicTimeZoneInformation (0 calls)
            - pid 101552: SystemTimeToTzSpecificLocalTime (0 calls)
            - pid 101552: SystemTimeToTzSpecificLocalTimeEx (0 calls)
            - pid 101552: FileTimeToLocalFileTime (0 calls)
            - pid 101552: LocalFileTimeToFileTime (0 calls)
            - pid 101552: TzSpecificLocalTimeToSystemTime (0 calls)
            - pid 101552: TzSpecificLocalTimeToSystemTimeEx (0 calls)
            - pid 101552: NtQuerySystemInformation (0 calls)
            - pid 101552: GetTimeZoneInformationForYear (0 calls)
  observed channels (hooked but left real):
            - pid 101552: NtCreateUserProcess (0 calls)
            - pid 101552: connect (0 calls)

A line is there only when it has something to say. A session that went well has no warnings and nothing left behind, so those lines are missing rather than empty.

The verdict

LineWhat it says
targetThe application, as you gave it.
browserIn the Chromium mode, the browser the session drove and its version.
stoppedCUT SHORT: --timeout ran out, or the session stopped answering. Everything below is what came in before that, so it is not the whole story.
verdictWhether the date reached the application, for the application and every process it started, with how many there were. The line under it says why. The verdicts are below.
refusedThe date did not reach the application, so the session ended it rather than let it run on the real date. --force lets it run on.
errorsSomething the session could not do while it ran, such as a jump to a date out of range. The session went on.
sessionWhere the session's clock got to, and how long the session took on the real clock and on the session's.
  • WORKS: every process that read the time got the session's date. The command ends with 0.
  • PARTIAL: some of it was read from the real clock, which the lines further down name. The command ends with 10.
  • DID NOT TAKE EFFECT: what the application read did not come from the session. The command ends with 11. With the target vanished right after injection instead, the application closed at once, most likely handing its work to a copy of it that was already running, and the command ends with 12.
  • UNDETERMINED: the session could not establish what it covered, which never counts as working. The command ends with 4.
  • DID NOT START: the session never began. The line under it says why, with a key in square brackets, such as [target.bitness_mismatch].

How the application ended

LineWhat it says
exitedThe code the application ended with, when it closed itself. It is not the code chrono ends with, which is the verdict. A crash is said in words, with the code Windows gives it.{{next_release}} Missing when the session ended first, as with --ticks.
followedPrograms the application started that were still running on the session's clock when it closed, so the session went on for them.
copies{{next_release}}Copies of the application that ran outside the session, on the real clock. A program that allows only one copy of itself most likely handed its work to one of them.

The clocks the application read

A channel is one of the ways Windows gives a program the time, named after the Windows function, such as GetLocalTime. Each row is one process, named by its pid, and its own count: counts are never added across processes, except in the total in the heading.

LinesWhat they say
covered channelsThe ones the session answered with its own date, and how many times the application asked. A count that reached the most the session can count says at least.
observed channelsOnes the session watches and leaves on the real clock on purpose, such as starting a process or opening a network connection, so they are never taken for covered.
uncovered channelsOnes the application asked and the session did not answer. They are what makes a verdict PARTIAL.
channels we meant to watch and could not hookA watch that did not start. The session did not miss the time there, it just cannot say how often it was asked.
channels hooked only once their module loadedThe session reached these only once the application loaded the part of Windows they live in, so the calls before that are not counted: their counts are the least there were.
processes this app spawned that the hook could not followProcesses the application started that ran on the real clock, by name. Usually ones of the other bitness, 64-bit from a 32-bit application or the other way round.
web engines reached inside the appA built-in web engine the session reached, with the port it reached it through. Its pages are the rows marked as contexts.

The time source audit explains why each of these is listed rather than counted as a pass.

Warnings and what was left behind

  • warnings: one sentence each about what to keep in mind, such as an application still running after the session, which is back on the real date, or a computer that slept, which stopped the session's clock. Each ends with its key in brackets, such as (session.left_running), the same key --json gives.
  • not fully cleaned up: what the session could not undo at the end, such as a temporary browser profile it could not delete, and what to do about it.

Troubleshooting says what to do about the warnings and errors that ask something of you, by their keys.

The file --report writes

--report session.txt saves the same report to a file, to attach to a ticket or keep with a test run. Two things are added:

  • A first line, !! UNRELIABLE EVIDENCE, when the session does not prove anything about the date: any verdict but WORKS, a session cut short, an application that never read a clock the session replaces, or a Go program, which reads the time where no session reaches.
  • Lines about the run at the end: the date and zone you asked for, the version of chrono, when the session started on the real clock, the application, the folder it ran in, its arguments and the options. The arguments are counted rather than written, since one may hold a password. --report-args writes them out.
  requested:  2038-01-19T03:14:07 (zone +00:00, mode flow)
  chrono:     0.6.0-rc.1, 64-bit core
  started:    2026-11-24T14:06:09Z (real clock)
  target:     C:\apps\test.exe
  folder:     C:\work (inherited from this command)
  arguments:  none
  flags:      none

In the window, the result screen shows the same facts, and Copy summary copies them: Run an app shows it. With --json the session writes them as JSON lines instead.
