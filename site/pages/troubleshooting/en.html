Troubleshooting

What to do when a session does not start, the application closes at once or it shows the real date. Each entry starts from what you see. The key the report gives for it, such as target.bitness_mismatch, stands beside it, so you can search this page for the key in your report.

The session did not start

  • The application and chrono.exe are different bitness (target.bitness_mismatch). On the command line a 64-bit application needs chrono.exe and a 32-bit one x86\chrono.exe: run the same command with the other one. The window picks the right one by itself. When the window says it anyway, the application runs at a different bitness than its file declares, as some .NET applications built for any CPU do: copy the diagnostics and report it.
  • The fake clock could not be attached to the application (target.inject_failed). An antivirus may have stopped it, or the application does not let other programs load code into it. When Windows Security reports a threat, the download page says how to exclude only the library Chrono Mock loads, not a whole folder. Electron and Chromium applications are reached another way and are not affected.
  • Part of Chrono Mock is missing (core.hook_dll_missing): chrono_hook.dll is not next to chrono.exe. Extract the whole package again, or install it again. When the file is gone again after that, check whether your antivirus removed it.
  • The application itself could not start: Windows did not find a library (DLL) it needs, or a library it loads is a different version, is built for the other bitness or failed to start (target.loader_dll_not_found, target.loader_entry_missing, target.loader_bad_image, target.loader_init_failed). Run it once without Chrono Mock, from the same working folder: Windows then names the file or the function it is missing.
  • Another Chrono Mock session is already running (session.already_active). One session runs at a time, so end the other one first, in the other window or the other chrono run.
  • The file is not a program Chrono Mock can start. It takes a .exe. Packaged Store applications (UWP and MSIX) are not supported. chrono run with --dry-run checks the file without starting anything.

The application closed right away

The window says Did not take effect - the application vanished, the report says the target vanished right after injection and the command ends with code 12. The line under it says which of these it most likely was:

  • A copy of it was already running (target.single_instance_suspected, session.handed_to_copy{{next_release}}). Many applications allow one copy only: a second start hands its work to the first and closes, and that copy runs on the real clock. Close every copy, also one that has only an icon by the clock or shows only in Task Manager, and start the session again.
  • It started another program the session could not enter (target.handed_off_uncovered), usually one of the other bitness, and that program runs on the real clock. When you know which program it starts, start that one instead.
  • It crashed (target.crashed, session.target_crashed){{next_release}}. Start it once without Chrono Mock to see whether it crashes there too. When it crashes only in a session, report it.
  • A Gecko application, with Chrono Mock running as administrator (target.restarted_without_admin){{next_release}}: see Running as administrator.

A console program that ends this fast is not counted here. It has done its work, and it gets a verdict.

The session was refused

The window says Refused - the fake clock did not take effect, so the session ended the application. The report's verdict is DID NOT TAKE EFFECT and the command ends with code 11. Right after the start the session found that what the application read did not come from the fake clock, and closed it, because a test on the real date proves nothing.

  • The lists under the verdict say what it read instead: the channels the session did not cover and the processes that ran on the real clock. The entries below give the usual reasons.
  • To keep the application running anyway, tick Start even if the fake clock turns out not to work, or add --force. The verdict and the exit code stay the same, and the session is marked unreliable.

The application shows the real date

The verdict says how much reached it: PARTIAL, code 10, means some of its time came from the real clock, and the lines under it say where from. Reading the report explains each of them.

  • Processes it started ran on the real clock (inheritance.children_uncovered, inheritance.child_not_injected). The report names them. Most often they are of the other bitness: a 64-bit helper of a 32-bit application, or the other way round.
  • It may read the time from a server (source.network_at_start). The report says so when the application opens a network connection. A time that comes from another computer, such as a server, a database or a licence service, is out of reach of any tool on this one.
  • It read none of the clocks the session replaces (coverage.session_clock_never_read). The session's clocks were in place and working, and nothing asked them: the application took its time from somewhere else.
  • It is a Go program (runtime.go_wall_clock_unreachable). Go reads the date straight from memory Windows shares with every program, where no session can reach it. The application sees the real date, shown in the session's time zone.
  • Its web pages show the real date: see the next section.

Web pages inside the application show the real date

  • An application with a built-in web engine (WebView2, Qt WebEngine). Reach the web pages inside the application is on from the start and puts its pages on the fake clock. Unticked, or with --no-embedded, they stay on the real date. When the report says the engine was not reached (embedded.webview2_not_reached, embedded.engine_unreachable, embedded.discovery_unavailable), its pages ran on the real clock. WebView2 and Qt WebEngine explains how the pages are reached.
  • The application runs as administrator (embedded.elevated_host): see Running as administrator.
  • An application on Mozilla's Gecko engine, such as Firefox (session.gecko_pages_sandboxed){{next_release}}. It runs its pages in processes inside the Gecko sandbox, which the session cannot enter. Tick Switch off the Gecko sandbox, or add --no-gecko-sandbox. The application then runs without that protection until it closes, so open only pages you trust in it.
  • An Electron application (chromium.main_process_uncovered). Its windows run on the fake clock, but its main process, the Node.js part outside the windows, reads the real one, and the session cannot reach it. A date it works out there, a reminder it schedules or a check it makes at start follows the real date. Electron and Chromium says more.

Running as administrator

Chrono Mock needs no administrator rights. Started as administrator, it starts the application as administrator too, and two kinds of application then slip out of the session:

  • The pages of a WebView2 application (embedded.elevated_host). WebView2 then ignores the setting the session reaches its pages through. Start Chrono Mock without administrator rights, or tick Reach the web pages of an application that runs as administrator (--elevated-embedded). That option writes one value to the machine's registry for the session and removes it at the end. While the application runs, any program on this computer can reach its pages.
  • A Gecko application (session.gecko_restarts_without_admin){{next_release}}. Started as administrator, it starts itself again without those rights, where the session cannot follow it, so it runs on the real clock. Chrono Mock says so before the session starts. Start Chrono Mock without administrator rights. When the application has to run as administrator, add --no-deelevate to Arguments under Speed and options, or to --args: it then stays in the session, running as administrator, so open only pages you trust in it.

A Chromium or Electron application starts empty

  • It starts as if it were just installed: not signed in, without your settings or extensions (chromium.launched_with_debug_port). The session starts it with a debugging port and a clean profile of its own, so it never runs on your real one. Sign in during the session when the test needs it: the profile and everything in it are deleted when the session ends.
  • A session with --user-data-dir or --remote-debugging-port in Arguments or --args does not start, because the session sets both itself. Take them out.
  • While the session runs, any other program on this computer can use that port to control the application.

Time does not run at the speed you chose

  • The clock runs faster, but timers and countdowns do not. Only the date and time follow the speed, unless you tick Also speed up timers and countdowns inside the application (--scale-duration). A wait for something else to happen, such as a file or another program, keeps its real length either way.
  • A stopwatch inside the application does not speed up (runtime.dotnet_stopwatch_qpc, runtime.python_monotonic_qpc, runtime.java_nanotime_qpc). .NET Stopwatch, Python 3.13+ time.monotonic and Java System.nanoTime read a precise counter that stays real unless you tick Also speed up timers that measure elapsed time (--scale-qpc). Animation and video timed by that counter can then look wrong.
  • At a high speed, short timers fall behind (timer.interval_floored, wait.timeout_collapsed). With timers sped up, at ×1440 a one-second timer would have to fire every 0.7 ms, more often than Windows allows: 10 ms for a window's timer, 1 ms for the others. It fires at that shortest step instead, and that part of the application runs slower than the session. A lower speed keeps more of them in step.
  • A minimized window slows down (chromium.background_timers_slowed). Chromium runs the timers of a hidden window about once a second. Tick Keep timers at speed in hidden windows (--keep-background-timers).
  • A network request fails at a high speed (wait.network_timeouts_scaled). A network library that times its own timeout from the time since Windows started, such as WinHTTP, follows the session speed, so a server slower than that timeout divided by the speed makes the request fail. Use a lower speed for that part of the test, or leave timers and countdowns at real speed.
  • A Unity game does not keep up (runtime.unity_delta_time_capped). The engine caps how far it moves the game on in one frame, so the gameplay stops following the speed well below it. The clock, dates and timestamps still follow.

Times are off by the time zone

  • A Node.js, Deno or Bun program shows no time zone name, or shows UTC (session.zone_unnamed){{next_release}}. Programs built on ICU cannot name some offsets on some dates. Choose a whole-hour offset from -12:00 to +14:00, or the offset of a real Windows time zone without daylight saving time, with the session starting on or after the date that zone took it.
  • A page, or a library of the application, may have read this computer's time zone instead of the session's (chromium.zone_is_host, embedded.zone_is_host, session.c_runtime_zone_kept{{next_release}}). The moment it shows is the session's, but the local time can be off by the difference between the two zones.

After the session

  • The application is still running (session.left_running). Stop session does not close it. It is back on the real date and time, and its counters carry on from where the session left them. Restart it for a clean run on the real clock.
  • A page inside it still shows the session's date (embedded.pages_not_released, embedded.zone_kept). Reload or close the page. A page that kept the session's time zone keeps it until the application restarts.
  • The application's data has future dates in it. An application that ran in 2038 wrote 2038 wherever it keeps its data, and Chrono Mock cannot take that back. Back up its data folder before a session, as the download page says.
  • The report says something was not fully cleaned up:
    • a temporary Chromium profile (cleanup.chromium_profile_left): delete it from your temp folder,
    • the browser the session started (cleanup.chromium_process_left){{next_release}}: when it still runs, end it in Task Manager,
    • a WebView2 option in the machine's registry (embedded.policy_value_left, embedded.policy_value_stale), which keeps a debugging port open for the application it names. Delete the value that contains --chrono-mock-session under HKLM\SOFTWARE\Policies\Microsoft\Edge\WebView2\AdditionalBrowserArguments. One left by an earlier session that ended abruptly also goes when you run Chrono Mock as administrator with --elevated-embedded once.

Reporting a problem

When none of this helps, open an issue on GitHub. The form asks for:

  • the version, in the window's title bar or from chrono version,
  • whether you used the window or the command line, whether the application is 32-bit or 64-bit and what it is built with, such as .NET, Java or Electron. You do not have to name the application,
  • the command or the steps, and the exit code,
  • the report: Copy summary in the window, or the file --report writes. When the window offers Copy diagnostics, add what it copies.

Read the report before you paste it. It holds the full path to the application, which on most computers contains your user name, and an issue is public. A security problem goes to a private report instead, never to an issue.
