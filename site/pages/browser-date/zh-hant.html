為測試變更 Chrome 或 Firefox 的日期

常見的答案是一個在頁面裡替換日期的擴充功能，或測試框架的時鐘。Chrono Mock 直接用獨立的時鐘啟動瀏覽器本身：每個分頁和每個 worker，任意日期，可凍結或加速，而 Windows 時鐘和其他所有程式都不受影響。

常見答案涵蓋了什麼

方法誰看到新日期漏掉了什麼
瀏覽器擴充功能它能進入的頁面裡的 JavaScript 日期往往一次只管一個分頁，而且不會告訴你漏掉了什麼
Chrome DevTools時區，透過 Sensors 面板裡的位置設定日期本身
測試框架的時鐘你寫的測試開啟的頁面手動測試，以及測試沒有驅動的每個頁面
Windows 時鐘整台電腦上的一切什麼都不漏，這正是問題：憑證、網域登入和時間同步也一起移動

Chrome

Chrome 以乾淨的一次性設定檔和本機偵錯連接埠啟動，每個頁面和 worker 都從工作階段取得 JavaScript 時間：Date.now, new Date(), performance.now, setTimeout, setInterval，以及工作階段的時區。瀏覽器本身保持真實日期，所以 HTTPS 網站照常載入 - 已在設為 2040 年的工作階段中驗證。 

# Chrome 處於 2027 年最後十秒，以六十倍速執行
chrono run "C:\Program Files\Google\Chrome\Application\chrome.exe" --at 2027-12-31T23:59:50 --mode x60 --args "http://localhost:8080/"

這個設定檔不是你的：沒有儲存的登入、沒有擴充功能，工作階段結束後即被刪除。其他以 Chromium 為基礎的瀏覽器同樣適用。 Chromium 模式如何運作 →

Firefox

Firefox 在工作階段進不去的沙箱處理程序中執行頁面，因此需要 --no-gecko-sandbox。這樣頁面會在沙箱外啟動，加入工作階段，跟隨它的時鐘、速度、跳轉和時區。在關閉之前，Firefox 都沒有這層保護，所以只在裡面開啟你信任的頁面。用 -no-remote -profile 加一個空資料夾給它一個獨立設定檔，這樣它不會把頁面交給你已經開啟的 Firefox。 

# Firefox 處於 2027 年最後十秒，使用獨立的設定檔資料夾
chrono run "C:\Program Files\Mozilla Firefox\firefox.exe" --at 2027-12-31T23:59:50 --no-gecko-sandbox --args "-no-remote -profile C:\ff-test http://localhost:8080/"

在 Firefox 中，移動的是整個瀏覽器而不只是頁面，憑證檢查也包括在內：在設為 2040 年的工作階段中，一個真實的 HTTPS 網站顯示了安全警告。來自檔案的頁面、你自己執行的測試伺服器，或網站憑證仍然涵蓋的日期，才是可行的情況。

以系統管理員身分啟動時，Firefox 會放棄權限並在工作階段之外重新啟動，除非它的引數裡有 --no-deelevate，工作階段從一開始就會說明這一點。

如何知道頁面拿到了日期

報告會說明工作階段到達了哪些頁面和 worker，哪些仍用真實時鐘：Chrome 按每個 JavaScript 內容，Firefox 按每個處理程序。 報告說明了什麼 →

它不做什麼

  • 伺服器端。 網站從自己伺服器拿到的日期仍是伺服器的日期。
  • 你日常用的瀏覽器。 工作階段啟動的是它自己的瀏覽器。它不會附加到你已經開啟的瀏覽器，也不碰其中的分頁和登入。
