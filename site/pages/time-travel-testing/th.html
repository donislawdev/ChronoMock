การทดสอบข้ามเวลา (time travel testing)

การทดสอบข้ามเวลาคือการรันซอฟต์แวร์ในวันที่อื่นที่ไม่ใช่วันนี้ เช่น เดือนหน้า วินาทีสุดท้ายของปี วันที่ 29 กุมภาพันธ์ หรือปี 2038 เพื่อดูว่าเมื่อวันนั้นมาถึงมันจะทำอะไร วิธีนี้หาบั๊กที่รอวันที่หนึ่งอยู่ เช่น รายงานที่ปิดงวดผิดเดือน ใบอนุญาตที่ไม่เคยหมดอายุ หรือโทเค็นที่ยังรับอยู่เกินไปหนึ่งวัน

ทำไมต้องมีเทคนิค

พฤติกรรมจำนวนมากขึ้นกับวันที่ ทั้งช่วงทดลองใช้และการหมดอายุของใบอนุญาต การต่ออายุการสมัครสมาชิก อายุของใบรับรองและโทเค็น การหมดอายุของแคช การปิดงวดสิ้นเดือนและสิ้นปี ดอกเบี้ย และการแจ้งเตือน ไม่มีอะไรในนี้ทดสอบได้ด้วยการรอ และทั้งหมดอ่านสิ่งเดียวกัน คือเวลาปัจจุบัน จากที่ใดที่หนึ่ง การทดสอบข้ามเวลาก็คือการควบคุม "ที่ใดที่หนึ่ง" นั้น

บางครั้งก็เรียกว่า time machine testing ไม่ว่าจะเรียกอย่างไร เวลาเลื่อนได้ในสี่ตำแหน่ง และแต่ละตำแหน่งเลื่อนส่วนที่ต่างกันของโลก

สี่วิธีเลื่อนเวลา

เวลาเลื่อนที่ไหนใครเห็นวันที่ใหม่เหมาะกับงานอะไรต้องแลกกับอะไร
นาฬิการะบบของเครื่องทุกอย่างบนเครื่องนั้นทดสอบตัวระบบปฏิบัติการเอง งานตามกำหนดเวลา บริการ บนเครื่องเสมือนที่ใช้แล้วทิ้ง ทดสอบได้ทุกอย่างการล็อกออนโดเมน ใบรับรอง และการซิงก์เวลาพัง และการเปลี่ยนต้องใช้สิทธิ์ผู้ดูแลระบบ
นาฬิกาในโค้ดโค้ดที่ถามนาฬิกานั้นการทดสอบหน่วยของโค้ดที่คุณแก้ได้ เช่น นาฬิกาที่ฉีดเข้าไป หรือไทเมอร์ปลอมของเฟรมเวิร์กทดสอบต้องมีซอร์สโค้ดและการออกแบบที่ส่งนาฬิกาเข้าไป ไม่ช่วยอะไรกับแอปที่คุณมีแค่ในรูปโปรแกรม
นาฬิกาของโปรเซสเดียวแอปหนึ่งตัวและโปรเซสที่มันเริ่มทดสอบแอปที่บิลด์แล้วตั้งแต่ต้นจนจบ บนเครื่องที่คุณใช้ทำงานแอปอาจอ่านเวลาด้วยทางอื่น คุณจึงต้องรู้ว่าการอ่านใดถูกครอบคลุม
เวลาของเซิร์ฟเวอร์ทุกอย่างที่ถามเซิร์ฟเวอร์นั้นแอปไคลเอนต์-เซิร์ฟเวอร์ที่เซิร์ฟเวอร์เป็นผู้กำหนดเวลาต้องควบคุมเซิร์ฟเวอร์ได้ ซึ่งไม่มีเครื่องมือในเครื่องตัวไหนให้ได้

บน Linux วิธีที่สามคือ libfaketime บน Windows ที่ผ่านมาคือ RunAsDate และนี่คือสิ่งที่ Chrono Mock ทำ ส่วนวิธีแรก และสิ่งที่มันทำพังบนเครื่องที่คุณใช้ทำงาน มีหน้าของตัวเอง →

เมื่อเวลาเลื่อนแล้ว ควรทดสอบอะไร

  • ขอบเขต - วันสุดท้ายของเดือน ไตรมาส และปีงบประมาณ และช่วงเวลาที่ปีเปลี่ยนขณะแอปกำลังทำงาน
  • ปฏิทิน - วันที่ 29 กุมภาพันธ์ วันที่ก่อนปี 1970 และขีดจำกัด 32 บิตในปี 2038
  • ใบอนุญาตของคุณเอง - วันสุดท้ายของช่วงทดลองใช้ วันแรกหลังจากนั้น และใบอนุญาตที่หมดอายุไปนานแล้ว
  • เวลาที่ผ่านไป - การนับถอยหลัง การหมดเวลาของเซสชัน และทุกอย่างที่วัดระหว่างสองช่วงเวลา ซึ่งจะเผยบั๊กก็ต่อเมื่อเวลาเดินเร็วกว่าความจริง
  • เขตเวลา - ลูกค้าที่อยู่ห่างไปห้าเขตเวลา ซึ่งวันของเขาจบก่อนวันของคุณ

การทดสอบข้ามเวลาของแอป Windows

Chrono Mock เริ่มแอปด้วยนาฬิกาของมันเองและไม่แตะนาฬิการะบบ ส่วนอื่นของเครื่องจึงยังใช้วันที่จริง นาฬิกาเริ่มได้จากช่วงเวลาใดก็ได้ หยุดนิ่ง เดินเร็วขึ้น หรือกระโดดขณะแอปเปิดอยู่ก็ได้ 

# แอปเห็นสิบวินาทีสุดท้ายของปี 2027 และข้ามไปปี 2028 เอง
chrono run "C:\apps\test.exe" --at 2027-12-31T23:59:50

# หนึ่งวันต่อนาที: ช่วง 30 วันจบภายในครึ่งชั่วโมง
chrono run "C:\apps\test.exe" --mode x1440

# ใช้สถานการณ์ที่มีชื่อแทนวันที่ และเขียนหลักฐานลงไฟล์
chrono run "C:\apps\test.exe" --preset month-end --report session.txt

# เริ่มด้วยวันนี้แล้วกระโดดไปปี 2038 หลังผ่านไปไม่กี่วินาที ขณะแอปเปิดอยู่
chrono run "C:\apps\test.exe" --jump-after 5:2038-01-19T03:14:05 --zone +00:00

ในหน้าต่างก็เช่นกัน เลือกแอป เลือกสถานการณ์หรือพิมพ์วันที่ เลือกความเร็ว แล้วกด Start

รู้ได้อย่างไรว่าการข้ามเวลาเกิดขึ้นจริง

ทุกเทคนิคมีจุดอ่อนเดียวกัน คือแอปอาจอ่านเวลาผ่านทางที่เทคนิคนั้นไม่ได้เลื่อน การทดสอบที่ผ่านเพราะแอปไม่เคยเห็นวันที่ใหม่เลยแย่กว่าไม่มีการทดสอบ ทุกเซสชันของ Chrono Mock จบด้วยคำตัดสิน ช่องทางเวลาที่แอปอ่านจริงพร้อมจำนวนครั้งของแต่ละช่องทาง และช่องทางที่พลาดไป การตรวจสอบทำงานอย่างไร →

สิ่งที่ไม่ครอบคลุม

  • โทรศัพท์และระบบอื่น Chrono Mock รันแอป Windows การทดสอบข้ามเวลาของแอป Android หรือ iOS หรือโปรแกรมบน Linux หรือ macOS ต้องใช้เครื่องมือของแพลตฟอร์มนั้น
  • ฝั่งเซิร์ฟเวอร์ วันที่ที่แอปได้รับจากเซิร์ฟเวอร์ยังคงเป็นวันที่ของเซิร์ฟเวอร์ เซสชันจะบอกเมื่อเห็นแอปเปิดการเชื่อมต่อเครือข่าย เพื่อให้คุณรู้ว่าต้องตรวจสอบ
