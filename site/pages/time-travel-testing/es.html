Time travel testing

El time travel testing consiste en ejecutar un programa en una fecha distinta de hoy - el mes que viene, el último segundo del año, el 29 de febrero, 2038 - para ver qué hace cuando llega ese día. Encuentra los errores que esperan una fecha: el informe que cierra el mes equivocado, la licencia que nunca caduca, el token aceptado un día de más.

Por qué hace falta una técnica

Mucho comportamiento depende de la fecha: periodos de prueba y caducidad de licencias, renovaciones de suscripciones, vigencia de certificados y tokens, caducidad de cachés, cierres de fin de mes y de año, intereses, recordatorios. Nada de eso se puede probar esperando, y todo lee lo mismo - la hora actual - de algún sitio. El time travel testing es controlar ese sitio.

A veces se le llama time machine testing. Se llame como se llame, el tiempo se puede mover en cuatro lugares, y cada uno mueve una parte distinta del mundo.

Qué probar cuando el tiempo ya se mueve

  • Los límites - el último día de un mes, de un trimestre y de un año fiscal, y el momento en que cambia el año con la aplicación en marcha.
  • El calendario - el 29 de febrero, una fecha anterior a 1970, el límite de 32 bits en 2038.
  • Tus propias licencias - el último día de una prueba, el primer día después, una licencia caducada hace mucho.
  • El tiempo transcurrido - cuentas atrás, caducidad de sesiones y todo lo que se mide entre dos momentos, que solo muestra sus errores cuando el tiempo corre más rápido que el real.
  • Las zonas horarias - el cliente a cinco zonas de distancia, cuyo día termina antes que el tuyo.

Time travel testing de una aplicación Windows

Chrono Mock inicia la aplicación con su propio reloj y deja en paz el reloj del sistema, así que el resto de la máquina conserva la fecha real. El reloj puede empezar en cualquier momento, quedarse quieto, correr más rápido o saltar con la aplicación abierta. 

# La aplicación ve los últimos diez segundos de 2027 y pasa sola a 2028
chrono run "C:\apps\test.exe" --at 2027-12-31T23:59:50

# Un día por minuto: un periodo de 30 días termina en media hora
chrono run "C:\apps\test.exe" --mode x1440

# Un escenario con nombre en lugar de una fecha, con la prueba escrita en un archivo
chrono run "C:\apps\test.exe" --preset month-end --report session.txt

# Empezar hoy y saltar a 2038 a los pocos segundos, con la aplicación abierta
chrono run "C:\apps\test.exe" --jump-after 5:2038-01-19T03:14:05 --zone +00:00

Lo mismo en la ventana: elige la aplicación, elige un escenario o escribe una fecha, elige una velocidad, pulsa Start.

Saber que el viaje en el tiempo ocurrió

El punto débil de todas las técnicas es el mismo: la aplicación puede leer la hora por un camino que la técnica no movió. Una prueba que pasa porque la aplicación nunca vio la nueva fecha es peor que no tener prueba. Cada sesión de Chrono Mock termina con un veredicto, los canales de tiempo que la aplicación leyó de verdad con un recuento de cada uno, y los que se perdieron. Cómo funciona la auditoría →

Qué no cubre

  • Teléfonos y otros sistemas. Chrono Mock ejecuta aplicaciones de Windows. El time travel testing de una app de Android o iOS, o de un programa en Linux o macOS, necesita una herramienta para esa plataforma.
  • El lado del servidor. Una fecha que la aplicación recibe de un servidor sigue siendo la del servidor. La sesión avisa cuando ve que la aplicación abre una conexión de red, para que sepas que hay que comprobarlo.
