Time Travel Testing

Time Travel Testing heißt, Software an einem anderen Datum als heute laufen zu lassen - nächsten Monat, in der letzten Sekunde des Jahres, am 29. Februar, im Jahr 2038 - um zu sehen, was sie tut, wenn dieser Tag kommt. Es findet die Fehler, die auf ein Datum warten: den Bericht, der den falschen Monat abschließt, die Lizenz, die nie abläuft, das Token, das einen Tag zu lange gilt.

Warum es überhaupt eine Technik braucht

Sehr viel Verhalten hängt vom Datum ab: Testzeiträume und Lizenzablauf, Abo-Verlängerungen, Laufzeiten von Zertifikaten und Tokens, Cache-Ablauf, Monats- und Jahresabschlüsse, Zinsen, Erinnerungen. Nichts davon lässt sich durch Warten testen, und alles liest dasselbe - die aktuelle Zeit - von irgendwoher. Time Travel Testing heißt, dieses Irgendwoher zu steuern.

Manchmal heißt es auch Time Machine Testing. Wie auch immer man es nennt: Die Zeit lässt sich an vier Stellen verschieben, und jede verschiebt einen anderen Teil der Welt.

Unter Linux ist der dritte Weg libfaketime. Unter Windows war es RunAsDate, und genau das macht Chrono Mock. Der erste Weg und was er auf einem Rechner kaputtmacht, an dem Sie arbeiten, hat eine eigene Seite →

Was testen, wenn die Zeit sich bewegt

  • Grenzen - der letzte Tag eines Monats, Quartals und Geschäftsjahres und der Moment, in dem das Jahr wechselt, während die Anwendung läuft.
  • Der Kalender - der 29. Februar, ein Datum vor 1970, die 32-Bit-Grenze 2038.
  • Ihre eigene Lizenzierung - der letzte Tag einer Testphase, der erste Tag danach, eine Lizenz, die vor langer Zeit abgelaufen ist.
  • Verstrichene Zeit - Countdowns, Sitzungs-Timeouts und alles, was zwischen zwei Momenten gemessen wird, und das seine Fehler erst zeigt, wenn die Zeit schneller läuft als in echt.
  • Zeitzonen - der Kunde fünf Zonen weiter, dessen Tag vor Ihrem endet.

Time Travel Testing einer Windows-Anwendung

Chrono Mock startet die Anwendung mit ihrer eigenen Uhr und lässt die Systemuhr in Ruhe, sodass der Rest des Rechners das echte Datum behält. Die Uhr kann zu jedem Moment starten, stillstehen, schneller laufen oder springen, während die Anwendung offen ist. 

# Die Anwendung sieht die letzten zehn Sekunden von 2027 und wechselt selbst nach 2028
chrono run "C:\apps\test.exe" --at 2027-12-31T23:59:50

# Ein Tag pro Minute: ein 30-Tage-Zeitraum endet in einer halben Stunde
chrono run "C:\apps\test.exe" --mode x1440

# Ein benanntes Szenario statt eines Datums, der Nachweis in eine Datei geschrieben
chrono run "C:\apps\test.exe" --preset month-end --report session.txt

# Heute starten und nach ein paar Sekunden nach 2038 springen, während die Anwendung offen ist
chrono run "C:\apps\test.exe" --jump-after 5:2038-01-19T03:14:05 --zone +00:00

Dasselbe im Fenster: Anwendung wählen, ein Szenario wählen oder ein Datum eingeben, ein Tempo wählen, Start drücken.

Woran man erkennt, dass die Zeitreise stattfand

Die Schwachstelle jeder Technik ist dieselbe: Die Anwendung kann die Zeit auf einem Weg lesen, den die Technik nicht verschoben hat. Ein Test, der besteht, weil die Anwendung das neue Datum nie gesehen hat, ist schlimmer als gar kein Test. Jede Chrono-Mock-Sitzung endet mit einem Urteil, den Zeitkanälen, die die Anwendung wirklich gelesen hat, mit der Anzahl je Kanal, und denen, die ausgelassen wurden. So funktioniert die Prüfung →

Was das nicht abdeckt

  • Telefone und andere Systeme. Chrono Mock führt Windows-Anwendungen aus. Time Travel Testing einer Android- oder iOS-App oder eines Programms unter Linux oder macOS braucht ein Werkzeug für diese Plattform.
  • Die Serverseite. Ein Datum, das die Anwendung von einem Server bekommt, bleibt das Datum des Servers. Die Sitzung meldet, wenn sie sieht, dass die Anwendung eine Netzwerkverbindung öffnet, damit Sie wissen, dass Sie das prüfen müssen.
